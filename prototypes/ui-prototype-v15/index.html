Help

How to use Judge the Judge, in plain language. Open a topic to read it.

What does this tool do?

A judge is a prompt that asks an LLM to review a text and report the errors in it. This tool tells you how far you can trust such a judge.

The idea is simple. You take texts that are correct and put errors into some of them on purpose, so you know exactly what is wrong where. Then you show every text to the judge and compare what it reported with what you planted.

One test case is one text for the judge, together with the list of errors you planted in it (the expected errors). A case with no planted errors is a clean case: the judge should report nothing in it.

The result answers two questions: how many of the planted errors did the judge find, and how often did it report an error that is not there?

How big does a test need to be?

The tool needs at least 30 planted errors and 10 clean cases before it gives a final answer. With fewer, one lucky or unlucky case changes the result too much, so the answer stays "Inconclusive". These two numbers are fixed.

Example. Write 10 clean cases. From each of them make one more case with 3 planted errors. That is 20 cases, so you run the judge 20 times, and you have 30 planted errors and 10 clean cases: exactly the minimum.

Two or three errors per case is a good number. Mark some errors as subtle (they need checking against the other text) and some as obvious, so the result shows whether the judge only catches the easy ones.

The Test cases step counts all of this for you under "Test size".

The four steps
  1. Judge. Paste your judge prompt, paste one real reply of the judge, and write the rules that say when the judge has reported an error.
  2. Test cases. Add clean cases, press "Add test case" to make a case with planted errors from a clean one, or import cases from a file (File menu). "Open" opens any case; "More" holds Clone and Remove; names must be unique. When the set is ready, finalize it.
  3. Run. For each case copy the prompt into your own LLM, copy its answer and press "Paste reply from clipboard". What the judge found appears right below the reply: the tool decides what is clear, and you decide the rest.
  4. Results. Read the numbers and export a report.

You can always go back to an earlier step to look. "Load demo data" fills everything in, so you can try steps 3 and 4 at once.

Working by hand: copy, run, paste

The tool never talks to an LLM itself. You copy a prompt, run it in the LLM of your choice, and paste the answer back. This happens in three places: running the judge (Run), asking for test data (Judge and Test cases), and asking for a second opinion (in the case window on Run).

On Run one case takes three clicks: "Open" (or "Next test case"), "Copy prompt", and after you copied the LLM's answer, "Paste reply from clipboard", which saves the reply at once. The first time, the browser asks whether the page may read the clipboard; allow it. If it does not work, open the box under the button, paste with Ctrl+V and press "Save reply".

A new reply for a case that already has one replaces it and resets that case: its decisions and proposals are removed and the automatic decisions are made again. The tool asks first only when you would lose decisions you set by hand or approved from an LLM opinion.

Run every judge prompt in a new conversation. Otherwise the judge remembers the previous case and one case can change the answer for the next.

The tool uses your judge prompt exactly as you wrote it and adds nothing to it.

Variables in the judge prompt

A variable is a name in double curly braces, for example {{source_text}}. It marks the place where the data of a test case goes. You can use any names; the tool has none of its own.

Every variable becomes one field of every test case. A prompt with {{source_text}} and {{summary}} gives test cases with two fields: source_text and summary.

One variable is the judged text: the output your judge evaluates, for example {{summary}}. Choose it under the prompt; the last variable is proposed. Planted errors always go into the judged text, so you never have to say where an error is.

If your prompt shows example JSON that contains two opening braces in a row, put a space between them, or the tool will read them as a variable. The list under the prompt shows what was found.

Sample reply, fields and error rules

Paste one real reply of your judge and press "Read sample reply". The tool lists the fields it found and where they are. For example claims[].verdict means: the field "verdict" of each item in the list "claims".

The tool does not guess what an error is. You say it with error rules. A rule has one or more conditions, joined by "all of these hold" or "any of these holds". Example: claims[].verdict equals contradicted. The judge has reported an error when at least one rule holds. To say "(A and B) or (C and D)", write two rules.

Each item of a list for which a rule holds is one finding. For each list, choose the field that holds the text the finding points at. The tool uses that text to match a finding to a planted error.

Under the rules you see at once which parts of your sample reply count as findings. A rule can only use fields that occur in the sample reply.

Error catalog

The error catalog is your list of the kinds of errors you plant, for example "wrong-number" or "unsupported-claim". Each category can have a short description and an example.

Only you add to it: type or paste one category per line, optionally as name - description. Add them here, or type a new name where you choose the category of an expected error: it joins this list at once. The results are grouped by category, so you see which kinds of errors the judge misses.

Clean base cases and cases with a planted error

A clean base case is a complete, correct input for the judge: a value for every variable and no errors. Type them in on the Test cases step, or copy the ready prompt into your LLM and paste what it returns.

To add a case, press "Add test case" on the Test cases step and choose a clean case or a case with errors. For a case with errors, pick a clean base case and a category, copy the prepared prompt into your LLM and paste its answer back, or press "Edit by hand". The errors always go into the judged text. You see the clean text and the changed text side by side, with the changed words marked, and the expected errors already filled in. Check them and save.

To correct a case later, press "Open". The case opens in a large window: the text on the left, the expected errors on the right. Each expected error takes three short lines: category and difficulty, fragment, description. Select words in the text and press "Use selected text as fragment", so you never retype them.

What the LLM returns is a proposal. Always check that the fragment (the exact changed words) is right, because the tool uses it to recognize whether the judge found the error.

Loading test cases from a file

"Load test cases" reads a CSV file (a spreadsheet) or a JSON file with up to 500 cases. Before anything is loaded you see a summary: how many cases, how many clean, and which rows cannot be read and why.

"Download example file" gives a small spreadsheet with the right columns for your judge prompt. One row is one case. Each field is a column named field: followed by the variable name. The expected errors go into one cell, like this:

wrong-number | "published in 1887" | The source says 1890 | subtle

That is: category, the exact fragment in quotes, a description, and optionally obvious or subtle. Separate several errors with ;; .

Deciding after each reply

As soon as you save a reply, the case window shows what the judge found. When the reply is valid JSON, the tool applies your rules and decides what is clear. A planted error is found when a finding points at its fragment. It is missed when nothing points at it and the judge reported nothing else in that case.

The rest waits for you, each with its reason. Typical reasons: the judge described the error in other words; the reply is not JSON; or the judge reported something you did not plant. Such an additional finding is never decided for you: you say whether it is a real error nobody planned or a false positive.

Second opinion. When the tool could not decide, your own LLM can propose an answer for that case. In the case window press "Copy verification prompt", run it, copy the answer and press "Paste LLM opinion from clipboard". The answer only fills in proposals with a short reason and the matching words. Nothing counts until you press "Approve", and you can change a proposal first. An opinion meant for another case is refused.

Ignore. If an item should not count at all, for example a planted error that turned out to be ambiguous, choose "ignore". It is left out of every number and listed as ignored in the report.

Every decision shows where it came from: automatic, set by hand, or an LLM opinion approved by the user.

Reading the results

The Summary shows the counts first: planted errors found and missed; additional findings, split into real errors and false positives; and the same for subtle errors.

Detection rate is the share of planted errors the judge found. Example: 26 found out of 30 is 87%.

False-positive rate is the share of the judge's findings that were wrong. Example: the judge reported 29 things in total and 2 of them were not errors: 2 out of 29 is 7%.

Limits. The result describes one judge prompt on one model. It only covers the kinds of errors you planted: a high detection rate says nothing about kinds of errors that were never in the test. The "95% interval" under Details shows how much the rate could move with other cases; it is a little too narrow when one case holds many errors.

While some cases have no reply or still await your decision, the numbers are marked provisional. You can export at any time; an exported report says it is provisional and how many cases are not decided.

The Results step only shows. "Open" in the Test case list shows a case without any way to change it; to change a decision, open the case on Run. Only the thresholds under "Details" can be changed on Results.

Judges that give only a verdict (for example bias: yes or no)

Some judges do not list problems; they answer for the whole text, for example {"biased": true} or a score. When every error rule uses only such fields, the tool evaluates the judge per case: the text was flagged or it was not. A case with planted errors that was flagged counts as found; one that was not flagged counts as missed. A flag on a clean case is shown to you, and you confirm whether it is a false positive.

The two case-level measures have thresholds of their own, with the same defaults (80% and 10%); only the thresholds of the measures in use apply and are shown under "Details". The result then shows two case-level measures: the case detection rate (cases with errors that were flagged, out of all cases with errors) and the clean-case false-positive rate (clean cases flagged wrongly, out of all clean cases). Example: 30 biased texts, 27 flagged: 90%. 10 neutral texts, 1 flagged: 10%. The test needs at least 30 cases with errors and 10 clean cases. The tool cannot tell which error such a judge found, only that it flagged the text.

Not covered in this version: graded answers such as "partly present", and checking a number the judge returns against a number you expected.

Overall result and thresholds

One line gives the overall result:

  • Works: the detection rate is at least 80% and the false-positive rate is at most 10%.
  • Does not work: one of the two is not met.
  • Inconclusive: some cases are not run or not decided, or the test is smaller than 30 planted errors and 10 clean cases.

You can change the two thresholds under "Details" on the Results step, or load them from a file with "Load check settings". The values used are saved with the result and printed in the report. "Borderline" means the result is close to a threshold and more cases would settle it.

Files

The tool remembers nothing after you close the page, so save your work to files. All of them are plain text you can open and read. You work with two files of your own, and every action for them is in the header: the "Save evaluation" button and the "File" menu. Each is saved the same way: the first save asks where, later saves overwrite that file (its name is shown in the "File" menu), and "… as" saves to a new file.

  • Test project ("Save test project", "Load test project"): the judge (prompt, sample reply, rules, catalog) together with all test cases (clean ones too), the active metric and the thresholds, and no replies. Load it again whenever you want to run the same test once more, for example with another LLM or other model settings. A test project saved after finalizing comes back finalized, ready for the Run step; "Edit test cases" opens it for changes as long as no reply has been entered.
  • Evaluation ("Save evaluation", "Load evaluation"): the whole progress of one run: the test project, every prompt, reply and decision, and the results. Load it alone later to continue, to see the result or to make the report again. After loading, the tool opens the step where work is left and "Continue" takes you to the first case that is not decided.
  • Test cases alone ("Export test cases", "Import test cases" in the File menu): JSON with all cases, or a shortened CSV (name and field:<variable>) whose rows all become clean cases. Not a remembered file.
  • HTML report ("Export HTML report"): for people; it can be read without the tool and printed to PDF.

Example of a check settings file:

{ "format": "judge-the-judge-checks", "schema_version": 1,
  "rules": [
    { "measure": "detection_rate", "comparison": "at_least", "value": 0.9 },
    { "measure": "false_positive_rate", "comparison": "at_most", "value": 0.05 } ] }

A metric definition ("Load metric definition") is a file that adds one more ready example to the Judge step, for another kind of judge. The folder examples next to this prototype holds two (bias-example.json, a judge that lists biased sentences, and bias-verdict-example.json, a judge that only says whether the whole text is biased) and a check settings file (checks-example.json).

Saved files and reports contain your full prompts, input data and replies. Handle them like the data itself.

Demo data

"Load demo data" loads a finished example: a judge that checks book summaries against their source, 10 clean cases, 10 cases with 3 planted errors each, and the judge's reply for every case. Five cases still wait for your decision on the Run step. A ready LLM opinion is already in the "Second opinion" paste box there, so you can press "Read LLM opinion" and "Approve all proposals" to see how that works.

Privacy and saving

Everything stays in this browser tab and in files on your own computer. There is no server and no temporary file anywhere else. Nothing is stored after you close the page; the tool warns you before you leave with unsaved changes.

Unsaved changes. The header always says whether everything is saved. It turns to "saved" after "Save evaluation". While you have entered no reply yet, "Save test project" is enough too, because the test project then holds all your work. Once replies exist, only "Save evaluation" keeps them.

One file for all your progress. The first "Save evaluation" asks where to save; every later "Save evaluation" overwrites that same file, so you never collect numbered copies. "Save evaluation as" saves to a new file, which then becomes the one that later saves go to. After "Load evaluation", saving goes to the file you loaded; the browser may ask once whether the page may change it. If the file was moved or removed, the tool says so and asks for a file again.

Browsers. The tool supports Google Chrome and Microsoft Edge. Other browsers may not allow saving to one file or reading the clipboard.

Save often. The Run step and the case window show how many replies are not saved to a file yet, and every 25 replies the tool reminds you to save. If the page stops responding, you lose only what was entered since the last save.
